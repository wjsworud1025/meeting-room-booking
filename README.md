# 회의실 예약 시스템

## 현재 개발 상태 · 2026-09-30

Railway에서 운영하는 Slack 연동 회의실 예약 시스템입니다. 현재는 단일 고객·단일 ADMIN 구조이며, 여러 수업장과 클래스 워크스페이스를 지원합니다. 고객별 데이터 격리를 갖춘 SaaS는 개발명세만 확정되었고 아직 구현되지 않았습니다.

- 예약: 30분–2시간 선택, 구성원 자동 참여, 충돌 방지, 예약 변경·취소, Slack 알림.
- 운영: 구성원 자동 동기화, 수업장별 회의실 접근 제한, 회의실 관리, 공휴일 기본 휴관과 여러 날짜 예외 개방.
- 클래스 추가: 7일 일회용 설치 링크, 취소·재발급, Slack 설치 후 클래스·수업장 자동 연결.
- 배포·개발 이력: [패치 및 브랜치 정리](PATCH-HISTORY.md), [Railway 운영](Railway-운영.md).
- 향후 구현 기준: [SaaS 개발명세 v1.0](최종개발명세서/SaaS-개발명세-v1.0.md).

실제 환경변수, Slack 인증 정보, DB 백업은 저장소에 포함하지 않습니다. `.env.example`을 참고해 환경을 별도로 구성하세요.

아래 로컬 실행 안내는 개발용 샘플 환경 기준이며 운영 계정·운영 로그인 방식과 다릅니다.

기존 목업의 이용자 시간표, 모바일 예약 신청, 관리자 휴관·초대·권한 회수 화면을 바탕으로 구현한 Next.js 앱입니다. PostgreSQL에 실제 저장하며, 서버에서 예약 충돌과 계정 권한을 검사합니다. 외부 계정 없이 로컬 이메일함으로 인증·알림을 확인합니다.

## 지금 사용하기

- 이용자: http://127.0.0.1:3000/login — `haneul@example.com`
- 관리자: http://127.0.0.1:3000/admin/login — `admin@example.com`
- 인증 코드: http://127.0.0.1:3000/dev/mailbox
- 다른 이용자: `jiwon@example.com`, `eunwoo@example.com`, `minseo@example.com`

로그인 화면에서 코드를 요청하고 로컬 이메일함에서 받은 코드를 입력하세요. 관리자와 이용자는 서로 다른 계정입니다. 이메일함의 인증 코드는 개발 전용이며, 실제 이메일은 발송하지 않습니다. 샘플 모집 예약도 실제와 동일하게 10분 뒤 만료됩니다.

## 다시 실행하기 (Windows, Node.js 24)

1. 최초 설치: `npm ci`
2. 첫 번째 터미널: `npm run db:local` — 이 터미널을 유지합니다. DB와 임의 비밀번호·세션 키를 생성하며 기존 데이터를 지우지 않습니다.
3. 두 번째 터미널에서 최초 한 번: `npm run db:migrate`, 이어서 `npm run db:seed` — 기존 계정이 있으면 샘플 생성을 건너뜁니다.
4. 두 번째 터미널: `npm run dev`, 이후 위 주소를 엽니다.

DB 종료는 첫 번째 터미널에서 Ctrl+C, 앱 종료는 두 번째 터미널에서 Ctrl+C입니다. DB는 `.local/postgres`에 보존됩니다. `.env.local`, `.local`은 Git 제외 대상이며 공유하지 마세요. 현재 DB 실행기는 Windows 전용입니다. 다른 운영체제에서는 PostgreSQL 17을 별도로 실행하고 환경변수를 설정해야 합니다.

단일 Next.js 프로세스 + PostgreSQL 구조입니다. Redis, 별도 API 서버, 별도 작업 서버 없이 동작합니다. `RUN_JOBS=true`이면 같은 프로세스가 2초마다 기한과 알림을 처리합니다. 클라이언트가 보내는 역할은 신뢰하지 않습니다. 데이터 변경은 공통 설정 행 잠금 후 권한·기한·충돌 검사와 함께 저장합니다.

## 운영 배포 전 남은 범위

이 버전은 로컬 검증판이며 최종 명세의 전체 인수 조건을 완료한 운영판은 아닙니다.

1. **외부 연결 검증:** Supabase 이메일 OTP, SMTP, 실제 관리자 초대·온보딩. 연결 코드는 있으나 실제 자격 증명으로 검증하지 않았습니다. 운영 로그인은 로컬 인증을 허용하지 않습니다.
2. **Slack:** 연결된 사용자에게 알림을 보내는 경로만 있습니다. 서명 검증 웹훅, 계정 연결, Slack 내부 조회·신청·수락 흐름은 미구현입니다.
3. **운영 기능 보완:** 회의실 추가·비활성화, 신고의 검토·기각 세부 상태와 이용자 처리 결과 화면, 실패 작업 관리자 재처리, 휴관까지 고려한 3운영일 제재 계산이 남아 있습니다.
4. **보관·복구:** 90일 자동 파기, 외부 Auth 삭제, 백업·복원 및 재처리 방지 검증이 남아 있습니다. 현재 자동 정리는 만료된 명령 처리 영수증에 한정합니다.
5. **운영 인수:** 명세 AT01–35 전체 추적 검증, 지속 부하·p95 측정, HTTPS·DB 최소권한·장기 실행 환경, 장애·복구 훈련이 필요합니다.

현재 API는 `GET /api/snapshot`, `GET /api/reservations/:id`, `GET /api/admin/data`, `POST /api/commands` 중심입니다. 명세의 개별 REST 경로를 그대로 구현한 형태는 아닙니다. 변경 명령은 `Idempotency-Key`와 `{name,input}`을 받으며 서버에서 권한과 버전을 검사합니다.

`npm run build`는 배포 빌드 검증용입니다. `npm start`는 운영 모드로 실행되어 로컬 OTP가 차단되므로, 외부 서비스 없이 체험할 때는 반드시 `npm run dev`를 사용하세요. `.env.example`에 외부 연결 항목이 있습니다.

원본 명세와 목업은 `최종개발명세서`, `목업-UI`, 시각 기획안은 `기획안` 폴더에 보존했습니다.

## 2026-09-29 변경

신규 예약과 추가 초대는 별도 수락 없이 자동 참여합니다. 구성원 전체의 일정·정원·공정성 검사에 통과해야 저장됩니다. 관리자 초대와 책임 이전은 기존 수락 절차를 유지합니다. 변경 전 대기 초대에는 이전 절차를 유지합니다.

날짜 입력 옆 달력 버튼에서 한국 공휴일·대체공휴일을 확인할 수 있습니다. 2026·2027년 자료를 포함하며 다른 연도는 자료 없음으로 표시합니다. 공식 공휴일 API 자동 갱신과 관리자 보정을 지원합니다. 실제 자동 조회는 HOLIDAY_API_KEY 설정과 서버 재시작 후 활성화됩니다. 휴일 표시와 시설 휴관은 별도입니다. 자세한 내용은 `최종개발명세서/03-자동참여-공휴일-변경명세.md`를 참고하세요.

## 공휴일 자동 갱신 설정

`시설·운영 설정 → 한국 공휴일 관리`에서 휴일을 직접 등록·수정하고 영향 예약을 검토할 수 있습니다. 공식 API 조회는 서버 `.env.local`에 `HOLIDAY_API_KEY`를 설정하고 재시작하면 활성화됩니다. 키는 공공데이터포털 한국천문연구원 특일 정보 활용 신청으로 발급받습니다. 올해·다음 해를 6시간마다 갱신하며 수동 보정과 마지막 정상 자료를 보존합니다. 정부 발표 직후 API 반영 지연에는 관리자의 근거 링크 기반 등록을 사용합니다.

- 상세 운영 방법: [공휴일 동기화 운영명세](최종개발명세서/04-공휴일-동기화-운영명세.md)
- 새 환경에는 `npm run db:migrate`로 `002_holidays.sql`까지 적용하세요.
- UI 검증: `npm run test:ui:holidays`
- 실제 공공 API 인증·응답은 서비스키가 없는 현재 환경에서 미검증입니다.

## 조회·로딩 최적화

예약은 3초 갱신을 유지하며 관리자 부가 자료와 공휴일은 60초 갱신 및 저장 직후 갱신을 사용합니다. 관리자 API는 `section`으로 조회 범위를 지정하며 이용자·관리자 화면 코드는 필요할 때 불러옵니다. 상세 변경 및 실측은 [최적화 적용 결과](최적화-적용결과-2026-09-29.md)를 참고하세요.

## 예약 처리 단순화

신규 예약은 중간 모집 상태 없이 같은 트랜잭션에서 확정하며, 참여자 자격 확인과 등록은 일괄 처리합니다. 예약 변경의 공정성 검사는 한 번만 실행하고 설정된 간격 안의 예약만 비교합니다. 기존 대기 초대·보충 기한·DB 중복 방지·재전송 보호는 유지합니다. 자세한 변경은 [예약 절차 패치 결과](예약절차-단순화-패치결과.md)를 참고하세요.

## 학생 UX 개선

연속 이용 가능한 시간만 제안하며, 신청 기간 밖·휴관·지난 시간·다른 예약의 사유를 구분합니다. 방·날짜·시간·구성원 초안은 계정별 sessionStorage에 보관하여 뒤로가기와 새로고침에도 유지합니다. 예약 완료·초안 버리기·로그아웃·인증 만료 시 삭제하며 서버에 초안 테이블을 추가하지 않습니다. 내 예약은 예정과 지난·취소 예약을 나누고, 작업별 확인·완료 문구와 날짜별 정책 안내를 제공합니다.

- UX 회귀 검증: `npm run test:ui:ux` (충돌 복구는 브라우저 응답 fixture이며 실제 예약을 만들지 않습니다.)
- 상세 결과: [UX 개선 패치 결과](UX-개선-패치결과-2026-09-29.md)

## 릴리즈 점검 (2026-09-29)

현재 판정은 **운영 출시 보류(NO-GO)**입니다. 로컬 검증 통과가 외부 서비스·복구·보존 기능의 인수를 대신하지 않습니다. 상세 결함 수정·알고리즘·워크플로우·잔여 조건은 [릴리즈 점검 결과](릴리즈-전체점검-2026-09-29.md)를 참고하세요.

- `npm run release:check`: 읽기 전용 설정·DB·작업 점검. 출시 차단 조건이 있으면 종료 코드 1. 비밀값은 출력하지 않습니다.
- `npm run test:api:release`: 샘플 학생으로 인증·권한·요청 검증과 로컬 동시 조회 측정.
- `npm run test:production:smoke`: 빌드 후 3101 포트의 임시 운영 모드 프로세스에서 개발 인증 차단 확인. 실제 외부 인증 성공은 검증하지 않습니다.
- `npm run test:ui:admin`: 관리자 작업 확인·CSV·정책·모바일 회귀 검사.

## 운영 연결 준비

`npm run release:prepare`로 별도 `.env.release.local`을 생성한 후 운영 서비스 정보를 입력합니다. 기존 개발 설정은 유지합니다. `npm run release:connections`는 메일·계정을 생성하지 않고 연결만 점검하며, `npm run release:check:production`은 해당 환경의 출시 조건을 검사합니다. 자세한 절차와 실제 수신 인수 양식은 [운영 환경 설정과 연결 검증](운영환경-설정과-연결검증.md)을 참고하세요.
