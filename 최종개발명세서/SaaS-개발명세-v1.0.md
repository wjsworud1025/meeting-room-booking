# 회의실 예약 SaaS 개발명세 v1.0

- 확정일: 2026-09-30
- 상태: 구현 기준 확정 / 구현·운영 이관은 별도 작업
- 목표: 관리자 개인이 독립된 고객으로 가입하여 자신의 운영 공간, 클래스, 회의실, 구성원과 예약을 관리한다.
- 기존 시스템은 첫 번째 고객 공간으로 이관한다. 기존 예약·회원·Slack 연결과 주소를 보존한다.
- 이 문서는 SaaS 전환 범위의 구현 기준이다. 기존 예약 정책·예외 개방·클래스 연결 기능은 여기서 명시적으로 변경한 부분 외에는 유지한다.

## 1. 제품 범위와 결정

| 항목 | v1 확정 사항 |
|---|---|
| 고객 단위 | tenant(운영 공간). 이메일·Slack 워크스페이스·수업장을 고객 식별자로 사용하지 않는다. |
| 소유자 | 운영 공간마다 활성 OWNER 정확히 1명. UI 명칭은 관리자. 기존 ADMIN과 대응한다. |
| 개인 계정 | 계정 하나는 활성 운영 공간 하나를 소유한다. 여러 공간 소유·운영진 초대·sub-admin은 v1 제외. |
| 구성원 | 연결된 클래스의 활성 Slack 구성원. 예약 이력과 무관하게 이용 대상이다. |
| 공간 구조 | 고객 → 수업장·과정 → 여러 클래스와 회의실. 기존 수업장 범위 제한 유지. |
| Slack | 동일 앱을 고객들이 설치한다. 워크스페이스 하나는 동시에 고객 하나의 클래스 하나에만 연결한다. |
| 호스팅 | Next.js 서비스 1개, PostgreSQL 1개. 고객별 tenant_id와 DB 접근 제한으로 격리. |
| 외부 서비스 | 기존 Supabase 인증, Slack, Railway, 공휴일 API 재사용. 운영 인증메일 전달 검증 필수. |
| v1 제외 | 유료 결제, 요금제, 고객별 도메인, 운영진 역할 계층, 고객 간 회의실 공유, 고객 전용 DB. |

데이터 귀속은 고객의 관리·내보내기·이전·삭제 권한으로 구현한다. 구성원의 개인정보 권리와 고객의 운영 권한은 별개이며, 이 명세는 개인정보의 법적 소유권을 선언하지 않는다. 고객에게 서버·DB 자격증명을 제공하지 않는다.

## 2. 계정과 권한

### 2.1 계정 모델

- accounts: 인증 주체. id, auth_subject(unique), 표시 이름, 인증 이메일, 상태. 이메일 변경과 무관한 영구 ID 사용.
- tenants: id, 표시 이름, owner_account_id, 상태(ACTIVE/SUSPENDED/DELETION_PENDING/DELETED), 생성 시각, auth_version.
- 같은 owner_account_id에 ACTIVE/SUSPENDED/DELETION_PENDING 공간을 중복 생성할 수 없도록 DB 제약 적용.
- 기존 members는 고객별 예약 이용 주체로 유지하고 tenant_id, account_id(nullable)를 추가한다. 로그인 주체와 예약 명단을 분리한다.
- 학생의 Slack 신원은 (team_id,user_id)로 확인한다. 이메일이 같다는 이유만으로 고객 간 계정·구성원을 합치지 않는다.
- 소유자 변경 시 이전 관리자 member는 비활성화하고 이력은 보존한다. 새 관리자 member만 활성화하며 tenants.owner_account_id와 같은 트랜잭션에서 변경한다.

### 2.2 권한표

| 주체 | 허용 | 금지 |
|---|---|---|
| 고객 OWNER | 자신의 공간 설정·클래스·회의실·예약·구성원·이력 관리, 데이터 내보내기, 소유권 이전, 탈퇴 | 다른 고객 데이터 접근, 서버 관리, 추가 관리자 발급 |
| 구성원 | 소속 고객 및 수업장의 예약 조회·신청, 자기 예약 관련 허용된 변경 | 관리자 API, 다른 고객·수업장 자원, 설치 요청 생성 |
| 서비스 운영자 | 배포·백업·장애 대응, 고객 상태 관리 | 일반 고객 관리자 세션을 통한 무제한 접근, 상시 고객 사칭 |

서비스 운영자 콘솔·인증 경로는 고객 UI와 분리한다. 지원 열람은 고객 공간·사유·유효기간이 있는 승인된 지원 세션으로 제한하고, 시작·조회·종료를 기록한다. 기본은 읽기 전용, 지원 세션 기본 만료 1시간. 장애 복구용 비상 접근은 별도 인프라 자격증명·접근 기록을 사용한다. 서버 운영자가 기술적으로 데이터에 접근할 수 없다는 보장은 하지 않는다.

### 2.3 인증

- 신규 소유자는 ID·비밀번호로 가입한다. 2026-09-30 사용자 확정에 따라 소유권 이전도 기존 ID 계정 로그인과 현재 비밀번호 재확인으로 수락한다. 가입 후 고객 공간 생성까지 재시도에 안전한 하나의 절차로 처리한다.
- 인증 발송 실패 시 가입 완료로 표시하지 않는다. 사용자 열거를 방지하는 중립 응답과 발송·검증 횟수 제한을 적용한다.
- 기본 로그인 세션 8시간. 선택한 '로그인 유지'는 최대 30일이며 서버에서 취소 가능한 세션으로 구현한다. 비밀번호·인증 코드를 저장하는 기능은 제공하지 않는다.
- 소유권 이전·데이터 내보내기·삭제는 최근 10분 이내 재인증이 필요하다. 로그인 유지 여부와 무관하게 적용한다.
- 요청마다 계정 상태, 고객 상태, 소유자 또는 구성원 소속, 세션 auth_version을 확인한다. 소유권 이전·탈퇴·접근 회수 시 이전 세션과 미사용 진입 토큰을 무효화한다.
- 여러 팀이 동일 ADMIN 비밀번호를 공유하는 기능은 v1 범위에서 제외한다. 고객당 개인 소유자 1명 모델을 따른다.

## 3. 데이터 구조와 격리

### 3.1 tenant_id 적용 대상

다음 데이터는 tenant_id NOT NULL이며 내보내기·삭제·권한 검증의 단위가 된다.

| 영역 | 대상 |
|---|---|
| 운영 | settings, venues, cohorts, rooms, policy_versions, opening_exceptions, 고객별 공휴일 수정·검토 정보 |
| 구성원 | members, sanctions, 고객별 Slack 신원 매핑·웹 진입 토큰 |
| 예약 | reservations, reservation_members, member_claims, reports |
| 연결 | slack_installations, slack_workspace_classes, class_install_requests |
| 시스템 작업 | tasks, command_receipts, audit_events, 내보내기 작업, 삭제 요청, 소유권 이전 요청 |

전국 공휴일 원본 캐시만 서비스 공통으로 유지한다. 고객의 수동 수정·휴관·예외 개방은 공통 캐시에 기록하지 않는다. 인증 계정과 Slack 워크스페이스 소유 라우팅은 별도 서비스 제어 영역에 둔다.

### 3.2 DB 제약

- 고객 소유 테이블에 UNIQUE(tenant_id,id)를 만들고 고객 간 참조가 가능한 모든 FK를 (tenant_id,참조_id) 복합 FK로 변경한다. 단순 UUID 유효성 검사만으로 참조를 허용하지 않는다.
- settings의 id=1 전역 구조를 tenant_id 기본키 구조로 전환한다.
- 정책 적용일 UNIQUE는 (tenant_id,effective_on), 수업장 이름 UNIQUE는 (tenant_id,name), 작업 중복 키는 (tenant_id,dedupe_key)로 변경한다.
- 관리자 단일성 제약은 tenant_id별 활성 ADMIN 1명으로 변경한다. 특정 이메일 하드코딩을 제거한다. 소유자 일치도 별도 검증한다.
- 방·구성원 중복 예약 방지 제약에 tenant_id를 포함하고 기존 시간 구간 [시작,종료) 의미는 유지한다. 고객별 구성원 ID 기준으로 충돌을 검사한다.
- Slack 워크스페이스 라우팅의 team_id는 서비스 전체에서 유일하게 유지한다. 소유 고객만 연결 해제할 수 있고 타 고객은 재설치로 소유권을 가져갈 수 없다.
- 일반 트랜잭션의 설정 행 잠금은 해당 고객 행에만 적용한다. 서로 다른 고객 요청이 전역 잠금으로 직렬화되지 않아야 한다.

### 3.3 요청·RLS 경계

- tenant_id는 인증 세션과 서버 소유 관계로 결정한다. URL·헤더·요청 본문의 tenant_id를 신뢰하지 않는다.
- 모든 고객 데이터 읽기·쓰기는 트랜잭션 내부에서 SET LOCAL 방식으로 검증된 고객 컨텍스트를 설정한 뒤 실행한다. 컨텍스트가 없으면 거부한다.
- 업무 테이블은 RLS ENABLE 및 FORCE 적용, SELECT/UPDATE/DELETE의 USING과 INSERT/UPDATE의 WITH CHECK 모두 검증한다.
- 웹·일반 작업 DB 역할은 슈퍼유저, 테이블 소유자, BYPASSRLS 권한을 갖지 않는다. 마이그레이션 역할은 별도이며 웹 프로세스에 주입하지 않는다.
- 커넥션 풀 반환·오류·트랜잭션 종료 후 컨텍스트가 남지 않아야 한다. 고객 B가 고객 A의 연결을 재사용하는 테스트를 필수로 둔다.
- UUID를 아는 것만으로 조회할 수 없어야 한다. 다른 고객 자원은 동일한 404 응답으로 처리해 존재 여부를 노출하지 않는다.
- 캐시 키·파일 경로·작업 dedupe·검색·다운로드·관리자 통계에도 고객 범위를 적용한다. API 필터만으로 격리를 구현하지 않는다.

### 3.4 작업자와 서비스 제어 영역

작업 선점은 별도 스케줄러 역할이 작업 ID·tenant_id·유형만 반환하는 제한된 경로로 수행한다. 실제 작업 payload 조회와 처리에는 해당 고객 컨텍스트를 설정한다. 일반 업무 역할에 전체 테이블 접근을 허용하지 않는다.

Slack 서명 검증 후 team_id로 고객 라우팅을 결정한다. 라우팅 조회는 서비스 제어 영역의 최소 정보만 반환하며, 이를 통해 임의 고객 데이터를 조회하지 못하도록 한다. 실패·재시도 작업도 최초 고객 ID와 예약 버전을 유지한다. 연결 해제·삭제 중인 고객의 외부 알림은 전송 전에 다시 차단한다.

## 4. 사용자 기능과 화면

### 4.1 고객 시작 흐름

ID 가입·로그인 → 운영 공간 이름 입력 → 수업장 생성 → 회의실 등록 → 클래스 설치 링크 발급 → Slack 설치 → 구성원 이용.

초기 설정 중인 고객에게 완료하지 않은 다음 단계 하나를 안내한다. 회의실이나 클래스가 없을 때 빈 시간표나 무한 로딩 대신 해당 설정 버튼을 제공한다. 기존 고객은 초기 설정 완료 상태로 이관한다.

### 4.2 고객 관리자 UI

- 주요 메뉴: 예약 관리 / 구성원·클래스 / 시설·운영.
- 보조 메뉴: 신고 / 변경 이력. 계정·내보내기·소유권 이전·탈퇴는 프로필의 운영 공간 설정으로 이동.
- 현재 운영 공간 이름을 명확히 표시한다. 다른 고객 공간 목록은 노출하지 않는다.
- 관리자는 모든 소속 수업장을 관리한다. 시설 전체 개방·휴관은 해당 고객 공간 전체만 의미한다.
- 고급 정책·기술 오류·변경 이력은 필요할 때 펼친다. 취소·기수 종료·데이터 삭제의 영향 안내는 유지한다.

### 4.3 구성원 UI

- 주요 메뉴: 예약하기 / 내 예약. 이용 안내는 보조 링크.
- 자동 참여한 예약을 내 예약에 통합하고 '내가 신청 / 초대받음'으로 구분한다. 참여 이력으로 구성원을 등급화하지 않는다.
- 소속 고객·수업장 회의실만 표시하며 서버도 동일한 범위를 검증한다.
- 학생용 Slack 앱에서 고객 소유자의 관리자 진입 토큰이나 다른 고객 예약을 노출하지 않는다. 공개 관리자 로그인 링크는 로그인 화면만 연다.

## 5. Slack 클래스 설치

기존 7일 만료·취소·재발급·일회용 링크 흐름을 유지하고 다음 조건을 추가한다.

| 단계 | 필수 동작 |
|---|---|
| 발급 | 인증된 소유자의 tenant_id를 요청에 기록. 해당 고객의 venue_id만 허용. |
| 안내 | 고객 공간·수업장·클래스 이름을 표시. 설치 담당자에게 예약 서비스 관리자 권한은 부여하지 않음. |
| OAuth 시작 | 유효한 링크만 허용. 서버 측 요청과 브라우저 state/cookie 연결. 토큰은 로그·분석 도구·참조 헤더에 노출 금지. |
| 콜백 | 앱 ID·scope·브라우저 state 확인 후, 고객 ACTIVE 상태·링크 만료·취소·재발급·미사용 상태를 다시 검사. |
| 연결 | 워크스페이스 전역 소유권, 설치 토큰, 클래스·수업장 연결, 링크 소비를 하나의 트랜잭션으로 처리. |

같은 링크의 동시 콜백은 하나만 성공한다. 이미 타 고객에 연결된 워크스페이스는 연결을 거절하고 기존 토큰·소유권을 덮어쓰지 않는다. 앱 삭제나 단순 연결 장애만으로 소유권을 다른 고객에게 넘기지 않는다.

워크스페이스의 고객 간 이전은 v1 자동 기능에서 제외한다. 필요할 때 기존 소유자 확인과 이력 보존을 포함한 지원 절차로 처리한다. 기존 고객 공간의 토큰·예전 설치 링크는 신규 고객 공간에서 사용할 수 없다.

## 6. 데이터 내보내기·소유권 이전·삭제

### 6.1 내보내기

재인증 → 내보내기 요청 → 고객별 비동기 작업 → 다운로드. 운영 공간, 수업장, 회의실, 클래스, 구성원, 예약·참여, 정책, 예외 운영, 신고·제재·변경 이력을 CSV/JSON ZIP으로 제공한다. 스키마 버전·생성 시각·시간대를 manifest에 포함하고 일관된 DB 스냅샷으로 생성한다.

비밀번호, Slack 토큰, 인증 비밀, 세션, 설치 링크 원문, 내부 서비스 로그는 제외한다. 파일 다운로드는 현재 소유자 인증을 다시 요구하고 24시간 후 만료·삭제한다. 실패한 내보내기는 성공으로 표시하지 않으며 재시도할 수 있다.

### 6.2 소유권 이전

현재 소유자 비밀번호 재확인 → 기존 대상 ID 지정 → 대상 계정 로그인·현재 비밀번호 재확인·수락 → 단일 트랜잭션으로 소유자 교체. 요청은 계정의 운영 공간 화면에 표시하고 24시간 동안 유효하며 취소 가능하다. 한 번 수락한 요청은 다시 권한을 변경하지 않는다. 대상이 이미 다른 공간을 소유하면 v1에서는 이전 불가 안내. 이메일 발송이나 이메일 인증은 요구하지 않는다.

이전 중에는 기존 소유자가 유지되고, 완료 순간 새 소유자 한 명만 권한을 가진다. 이전 완료 시 이전 소유자 세션·진입 토큰·미완료 이전 요청을 폐기하고 양쪽에 결과를 알린다. 구성원·예약·Slack 설치는 유지한다. 과거 처리자는 원래 계정으로 남긴다.

### 6.3 삭제

재인증 → 내보내기 안내·진행 예약 영향 표시 → 공간 이름 입력 확인 → 7일 삭제 대기 → 실제 삭제.

- 대기 동안 신규 예약·관리 변경·설치·알림을 중지한다. 소유자는 내보내기와 삭제 취소만 가능하다.
- 취소하면 ACTIVE로 복귀한다. 이미 시간상 종료된 예약을 되돌리거나 중지 중 알림을 일괄 재발송하지 않는다.
- 7일 후 업무 데이터·연결 비밀·다운로드 파일을 삭제하고 최소 삭제 작업 증빙만 비식별 형태로 보관한다.
- 백업은 삭제 확정 후 최대 30일 내 만료되도록 정책을 설정한다. 복구 시 삭제 원장을 재적용하여 삭제 고객을 되살리지 않는다.
- 이 기간은 제품 목표이며 실제 호스팅·백업 설정에서 달성 여부를 검증해야 한다. 검증 전 '완전 삭제' 안내를 출시하지 않는다.

## 7. API와 실패 처리

모든 변경 요청은 서버 권한 검증·입력 검증·idempotency·변경 이력을 적용한다. 고객 ID를 클라이언트가 선택하는 공통 관리 API를 만들지 않는다.

| API 영역 | 계약 |
|---|---|
| 인증·초기 설정 | 본인 인증, 고객 공간 생성, 세션 해제. 중복 클릭 시 운영 공간 중복 생성 금지. |
| 기존 예약·관리 명령 | 기존 명령 이름 유지 가능. 고객 컨텍스트와 복합 참조 검증을 공통 계층에서 강제. |
| 클래스 설치 | 기존 create/reissue/revoke 유지. 현재 고객 요청만 조작. 공개 페이지는 설치에 필요한 최소 정보만 반환. |
| 공간 관리 | 내보내기 생성·상태·다운로드, 소유권 이전 생성·취소·수락, 삭제 요청·취소. |
| 운영 지원 | 고객 UI와 분리. 지원 권한·접근 시간·사유와 감사 기록 필수. |

실패 시 사용자 입력을 유지하며 재시도 방법을 보여준다. 만료 세션은 재로그인을 안내한다. 이미 처리된 요청은 같은 결과를 반환한다. 소유권 변경·고객 정지·자원 버전 변경은 저장 직전 다시 확인한다. 실패 트랜잭션에서 토큰·권한·데이터의 일부만 저장하지 않는다.

## 8. 기존 서비스 이관

| 단계 | 작업 | 통과 조건 |
|---|---|---|
| 1 준비 | 운영 백업·복원 리허설, 현행 데이터 수량·연결 목록 기준값 기록. 테스트 환경에 복제하되 비밀값·불필요한 개인정보 최소화. | 복원 검증 및 이관 소요시간 실측 완료 |
| 2 확장 | tenants/accounts와 nullable tenant_id 추가. 첫 고객 및 현재 소유자 생성. 신규 쓰기는 첫 고객 ID를 함께 기록. | 기존 코드 호환, 신규 레코드 누락 없음 |
| 3 채우기 | 기존 데이터 tenant_id 백필. Slack 연결·작업·이력·예외·정책 포함. 기존 UUID와 예약 시간 유지. | NULL·고아 참조 0건, 기준 데이터 대조 통과 |
| 4 격리 | 고객 범위 코드, 복합 FK·고객별 제약·RLS·권한 분리 적용. 기존 세션은 검증된 회원에서 고객을 결정하거나 안전하게 재로그인 유도. | 고객 A/B 격리 테스트 전부 통과 |
| 5 개방 | 첫 고객으로 운영 검증 후 신규 고객 가입 활성화. | 기능·알림·복원·삭제 기준 충족 |

목표는 서비스 중단 없는 전환이다. 실제 잠금·마이그레이션 리허설 결과에 따라 짧은 쓰기 제한이 필요하면 사전에 명시한다. 검증 없이 무중단을 보장하지 않는다.

두 번째 고객 생성 이후에는 고객 격리가 없는 구버전으로 롤백하지 않는다. 신규 가입을 중지하고 격리를 유지하는 패치로 복구한다. 백업 복원은 복원 시점 이후 데이터 손실 범위를 확인한 후 수행한다. 기존 운영 DB를 로컬 DB로 덮어쓰지 않는다.

## 9. 출시 통과 기준

### 기능

- 새 소유자 인증부터 공간·수업장·회의실·클래스 연결과 구성원 예약까지 완료된다.
- 기존 고객의 예약·취소·예외 개방·구성원 동기화·Slack 알림이 유지된다.
- 고객별 소유자는 정확히 1명이며 동시 이전·탈퇴 요청에도 위반하지 않는다.
- 내보내기 및 삭제 대기·취소·실제 삭제·백업 복원 후 삭제 원장 재적용을 검증한다.

### 격리: 반드시 실패해야 하는 요청

고객 A 세션으로 고객 B의 방·예약·구성원·수업장·정책·설치 요청·신고·감사 이력·내보내기 파일을 조회·수정·삭제하는 요청을 각각 테스트한다. 직접 ID 입력, 중첩 참조, 목록 검색, 캐시 재사용, Slack 콜백, 만료 링크, 백그라운드 작업도 포함한다.

DB 역할에서 고객 컨텍스트 없이 접근, 다른 고객 FK 삽입, 고객 ID 변경 UPDATE가 모두 거부되어야 한다. 풀 연결을 교대로 재사용하고 예외·롤백 뒤에도 데이터가 섞이지 않아야 한다. 다른 고객의 존재 여부·인원수·예약 시간도 응답에 포함하지 않는다.

### 동시성·경계

- 같은 시간 같은 방 예약 2건 중 하나만 성공. 서로 다른 고객의 예약은 불필요하게 차단하지 않음.
- 같은 설치 링크·같은 워크스페이스 동시 연결은 소유권 한 개만 생성.
- 예약 저장 도중 기수 종료·고객 정지·권한 회수가 일어나도 부적격 접근 차단.
- 날짜 경계·공휴일·예외 개방·30분/120분·참여 정원·일정 겹침 기존 회귀 테스트 유지.
- 느린 응답·중복 클릭·새로고침·뒤로가기·모바일·키보드 조작 시 중복 생성과 입력 유실을 검증.

### 운영

웹 DB 역할의 BYPASSRLS/소유자 권한이 없음을 실제 배포 환경에서 확인한다. 설치 토큰·인증 코드·개인 데이터가 일반 로그에 남지 않는다. 데이터 복원과 고객 삭제 절차가 실행 가능하며 오류 시 담당자가 확인할 수 있다. 기존 단위 테스트 통과만으로 SaaS 출시 승인을 대체하지 않는다.

## 10. 구현 묶음과 완료 정의

| 순서 | 개발 묶음 | 완료 산출물 |
|---|---|---|
| A | 고객·계정 모델, DB 제약, 첫 고객 백필 | 마이그레이션·리허설 보고서·호환 경로 |
| B | API/RLS·Slack·작업자·캐시 고객 격리 | 교차 고객 실패 테스트·운영 권한 검증 |
| C | 가입·초기 설정·고객 UI·클래스 설치 연결 | 관리자/구성원 브라우저 검증 |
| D | 내보내기·소유권 이전·탈퇴·운영 지원 | 수명주기 및 복원 검증 |
| E | 기존 운영 이관·신규 가입 개방 | 전체 통과 기준과 알려진 제한 기록 |

A와 B가 통과하기 전에는 두 번째 실제 고객을 운영 DB에 등록하지 않는다. 구현 일정은 A의 스키마·데이터 이관 리허설 결과를 기준으로 산정한다. 이 문서 확정은 코드 변경·배포·고객 데이터 삭제를 수행했다는 의미가 아니다.
