# SaaS 운영 전환·복구 절차 v1.0

기준일: 2026-09-30 · 대상: Railway meeting-room-booking · 개발 브랜치: codex/saas-data-isolation

최신 판정: 사용자 배포 승인 후 기존 고객 제한 운영을 시작했다. [2026-09-30 운영 배포 기록](SaaS-운영배포-2026-09-30.md)을 우선한다. 아래는 전체 공개 출시 기준이며, 신규 고객 가입·영구 삭제를 포함한 공개 출시는 여전히 차단한다. 이 문서는 운영 변경을 실행하는 스크립트가 아니다.

## 1. 전환 가능 여부

| 항목 | 확인된 증거 | 운영 통과 조건 |
|---|---|---|
| 데이터 격리 | 합성 A/B 고객의 실제 API 핸들러·DB RLS 검사 통과 | 배포할 정확한 커밋과 실제 제한 역할로 재현 |
| 실제 데이터 | 승인된 24개 테이블: 업무 274행·마이그레이션 15행·import 1행 및 시퀀스 복원. PostgreSQL 18.6에서 016 및 후보 001–005 적용·롤백 후 모든 테이블 지문 일치 | 실제 전환 직전 새 백업, 비밀 설정 버전·운영 역할·볼륨 복구 계획 확정 |
| Slack | 테스트 앱 설치·홈·웹 진입·본인 예약/취소 DM 확인 | 두 실제 구성원의 예약·초대·취소, 고정 HTTPS와 운영 앱 라우팅 확인. 합성 참여자 시험으로 대체하지 않음 |
| 자동 작업 | 고객별 NOTIFY, 공휴일 공유 작업 단일 선점·실패 시 캐시 유지·수동 변경 보존 검사 통과. 레거시 MEMBER_PROVISION 차단 | 운영 워커 역할 설치와 제한된 실제 Slack 수신자 검증 |
| 배포·인증 | 로컬 스테이징 역할 3개, ID 로그인 및 첫 비밀번호 변경 검사 | 운영 역할 설치·권한 검사·마이그레이션 전용 실행기, hyundai_1st 소유권 연결 및 최초 비밀번호 변경 완료 |

운영 DB에는 이번 확인 시점에 identity 스키마가 없었다. 로컬의 hyundai_1st 계정이 운영에도 존재한다고 가정하지 않는다. 임시 비밀번호 1111은 사용자가 요청한 초기값이며 서비스 개방 전에 반드시 변경한다. 비밀번호·해시·연결키를 문서나 로그에 기록하지 않는다.

## 2. 릴리스 묶음과 백업 범위

하나의 릴리스 묶음에 앱 커밋, 마이그레이션 파일 SHA-256, PostgreSQL/확장 버전, 역할 권한 정의, 환경변수 이름 목록, 비밀 저장소의 버전 참조, 백업 식별자와 검증 보고서를 연결한다. 아직 미커밋 변경이 있으므로 현재 작업 폴더를 확정 릴리스로 취급하지 않는다. 비밀값은 Git에 넣지 않는다.

| 보존 대상 | 처리 원칙 |
|---|---|
| booking 전체 및 존재하는 identity·saas_control | 예약·구성원·시설·설정·감사 외에 신고·제재·설치 요청·작업·세션 등 서비스 복구에 필요한 범위를 별도로 승인·확정. 제외 데이터가 있는 백업은 전체 복구용으로 사용하지 않음 |
| public 마이그레이션 원장·시퀀스·제약·확장·역할 | 앱 데이터만 복구하고 적용 원장이 어긋나지 않도록 함께 검증. DB 복원 뒤 마이그레이션을 무조건 재실행하지 않음 |
| Slack 암호화키·앱 인증정보·세션키·연결 설정 | 암호화된 설치 토큰에 대응하는 키 버전 보존. DB 백업과 키를 같은 파일로 전달하지 않음 |
| 알림 작업과 외부 전송 이력 | 백업 복구만으로 이미 전달된 DM을 되돌릴 수 없음. DONE/RUNNING/PENDING 및 전송 결과 대조 후 재개. 일괄 초기화·무조건 재전송 금지 |
| 복구 접근 수단 | 복호화·권한·복원 실행을 실제 검증. 임시 SSH 키는 작업 후 해제. 로컬 백업은 암호화하며 복제본의 웹·Socket·워커는 실행하지 않음 |

최신 `.local/backups/railway-1790744899443` 자료는 추가 승인받은 신고·제재·설치 요청·작업 큐·임시 링크·명령 처리 기록·public 원장을 포함한 명시적 24개 테이블과 holiday_override_version 시퀀스의 암호화 백업이다. 스키마 와일드카드는 사용하지 않았다. 복원 DB의 Slack 토큰은 현재 운영 암호화키로 복호화 가능함을 메모리에서 검증했다. 원본은 읽기 전용이며 임시 SSH 키 등록은 해제했다. 글로벌 역할·환경변수 원문·볼륨·WAL을 포함하는 완전한 인프라 백업으로 표현하지 않는다.

## 3. 운영 전환 순서

| 단계 | 실행 | 통과 기준 / 실패 시 행동 |
|---|---|---|
| 1. 준비 | 위 조건 충족, 릴리스 묶음 확정, 유지보수 시간 공지, 이전 앱·복구 자격증명 확보 | 실측 복원 시간과 여유 시간을 바탕으로 중단 시간 확정. 현재 RTO/RPO 실측 보장 없음. 하나라도 누락되면 시작하지 않음 |
| 2. 쓰기 동결 | 웹 예약·관리·가입·설치 변경 진입 차단, Socket 수신 처리·워커·명단 동기화·다른 실행 인스턴스 정지, 진행 중 DB/외부 작업 종료 확인 | DB 변경이 멈췄음을 확인한 뒤 최종 백업 및 원본 지문 확보. RUN_JOBS=false만으로 웹·Slack 쓰기가 막혔다고 간주하지 않음 |
| 3. 이관 | 전용 마이그레이션 연결로 기존 원장 확인 후 필요한 016 적용 → hyundai_1st와 기존 ADMIN 연결 → 001_candidate → 002_web_runtime → 003_slack_workers → 004_shared_jobs → 005_lifecycle. 후보 SQL과 데이터 검증은 트랜잭션으로 묶고 실패 시 롤백 | 단일 OWNER, 기존 UUID·토큰 보존, 행수·지문 일치, 고객 ID 누락 0. 기존 소유자 매핑을 덮어쓰지 않음. 잠금·SQL 제한시간은 리허설 실측으로 지정 |
| 4. 제한 기동 | 운영용 역할 적용·검사 후 새 앱을 점검 접근만 허용해 시작. 마이그레이션 자격증명은 앱에서 제거. 워커·신규 고객 가입은 계속 정지 | 첫 고객 관리자 로그인·비밀번호 변경·회의실·구성원·기존 예약 조회, 학습자 권한, 로컬 주소 잔존 여부 검사. 실패 시 4절의 쓰기 전 복구 |
| 5. 개방 | 첫 고객의 제한된 실제 예약·초대·취소 확인 → 작업별 재개 → 모니터링 → 두 번째 고객 개방 | 시험 예약도 신규 쓰기로 취급. 고객 교차 접근·잘못된 DM·데이터 누락이면 즉시 쓰기 및 작업 중지. 첫 고객 검증 전 일반 가입을 개방하지 않음 |

현재 `scripts/start-railway.mjs`는 앱 DATABASE_URL을 MIGRATION_DATABASE_URL로 복사하고 자동 마이그레이션·기존 import를 실행한다. 이 실행기를 그대로 사용하거나 차단 한 줄만 제거해서는 안 된다. SaaS 운영 실행기는 이관과 앱 시작을 분리하고, 웹/인증/작업의 비특권 연결을 검사한 뒤 프로세스만 시작해야 한다. `saas:staging:start`는 로컬 스테이징 전용이므로 운영에 사용하지 않는다.

역할 계약은 DATABASE_URL=고객 업무 CRUD/RLS, CONTROL_DATABASE_URL=인증 및 제한된 라우팅 함수, WORKER_DATABASE_URL=작업 선점·상태 검사 함수다. SUPERUSER·BYPASSRLS·소유자 역할 상속이 없어야 하며 테이블 직접 접근 금지와 함수 PUBLIC 권한 제거를 실제 연결별로 확인한다.

## 4. 장애 중단·복구 판단

| 발생 시점 | 복구 방법 | 재개 조건 |
|---|---|---|
| 이관 트랜잭션 완료 전 | 실패 트랜잭션 롤백. 별도 적용한 로그인 스키마/계정 변경 여부까지 기록하고 이전 앱 호환성 확인 | 이전 앱·DB 검증 후 기존 서비스 재개. 일부 DDL 성공을 전체 롤백으로 오인하지 않음 |
| 이관 완료 후, 새 업무 쓰기 없음 | 서비스를 정지한 상태에서 최종 전체 백업을 새 비공개 DB로 복원. 이전 앱·환경 설정·키 버전과 함께 연결 전환 | 원본 지문, 관리자 접근, 예약 조회, 작업 상태 검증. 원본·실패 DB는 보존하고 덮어쓰기/삭제는 별도 확인 |
| 시험 예약을 포함한 새 쓰기 발생 후 | 즉시 쓰기·외부 발송 중지, 변경 후 DB 보존. 수정 배포 또는 새 예약·취소·회원·설치 변경을 대조한 복구안을 선택 | 사전 백업 단순 복원 금지. 유실/재처리 목록과 영향 확인 및 승인 후 복구. 감사 로그만으로 완전 재실행 가능하다고 가정하지 않음 |
| DM 성공 여부 불명·중복 가능 | 해당 작업 보류, 고객·예약·수신자·Slack 전송 결과 대조 | 발송 대상과 결과 확인 후 제한 재시도. 정확히 한 번 발송을 보장하지 않음 |
| 고객 간 데이터/알림 혼선 | 신규 쓰기·가입·외부 발송 즉시 중지, 관련 고객 연결 차단 및 증거 보존 | 격리 원인 수정과 양방향 A/B 회귀 검증 후 재개. 앱 프로세스 재시작만으로 해결 처리하지 않음 |

스키마만 되돌리거나 앱 버전만 되돌리는 방식은 사용하지 않는다. 복구 후 기존 세션·일회용 링크를 유지할지 폐기할지 결정하고 재로그인 영향을 안내한다. 복구 DB의 워커는 대기 작업 정합성 확인 전까지 정지한다.

## 5. 실행 증거와 다음 구현

릴리스별 기록에는 실행자, 시작/종료 시각, 커밋, 백업/키 버전 참조, 전후 행수·지문, 적용 마이그레이션, 역할 검사, 정상/오류 시험, 최종 승인·중단 사유를 남긴다. 사용자 원문 데이터·토큰은 기록하지 않는다.

마이그레이션과 앱 기동을 분리한 실행기, 최소 역할 설치·검사, 별도 워커, 공휴일 공통 작업 및 레거시 구성원 등록 차단을 구현했다. 내보내기·ID 기반 소유권 이전·삭제 대기/취소와 합성 데이터의 영구 삭제·원장 재적용도 통과했다. 출시 차단은 유지한다. 남은 운영 조건은 별도 삭제 원장 보존·백업 30일 만료 검증, 운영 역할 적용, 두 실제 Slack 구성원의 예약/초대 검증이다.

관련 증거: [복원 리허설](SaaS-이관-복구-리허설.md), [스테이징 검증](SaaS-스테이징-검증.md), [Slack 작업 격리](SaaS-Slack-알림-격리.md). 이전 문서의 초기 미완료 목록보다 이 문서의 기준일과 실제 검증 기록을 우선 참고한다.


## 운영 실행기·권한 검사 구현 (2026-09-30)

- `scripts/saas/runtime-check.ts`: 세 연결의 같은 DB·서로 다른 역할, HTTPS origin, 세션키 길이, Slack 필수 설정, 명시적인 자동 작업 설정을 검사한다. 마이그레이션 자격증명과 초기 관리자 비밀번호가 런타임 환경에 남아 있으면 거부한다.
- 각 연결에서 읽기 전용 트랜잭션을 열어 특권·다른 역할 멤버십·테이블 소유 역할·스키마/DB 생성 권한을 검사한다. 테이블·열·시퀀스 권한은 역할별 허용 범위와 대조한다. 고객 21개 테이블의 RLS/FORCE RLS, 무컨텍스트 조회, 제어 함수 존재·실행권·PUBLIC 권한·SECURITY DEFINER 검색 경로를 확인한다. 작업 선점 함수를 실행하지 않는다.
- `scripts/saas/start-production.ts`: 자동 migration/import 없이 Next와 선택적 Socket 프로세스를 시작하는 후보. 자식 실패 시 함께 종료한다. 현재 코드의 출시 게이트가 모든 실제 기동을 `SAAS_RELEASE_NOT_READY`로 차단한다. 환경변수 우회 옵션은 없다.
- `npm run saas:runtime:check`: 이미 환경에 주입된 설정만 검사한다. 비밀 파일은 자동 탐색하지 않는다. `npm run saas:start`: 현재는 출시 차단으로 종료한다. 기존 Railway 시작 경로는 바꾸지 않았다.
- RUN_JOBS=true는 별도 작업 프로세스로 실행하도록 검사·구현했다. SAAS_DELETION_ENABLED=true는 별도 원장 보존과 백업 만료 검증 전에는 DELETION_RETENTION_NOT_READY로 거부한다. 검사 통과 자체는 운영 배포 승인이나 모든 RLS 정책 의미의 검증이 아니다.

검증: TypeScript 통과, 20개 파일 132개 단위 테스트 통과, 임시 DB의 정상 역할 통과/과다 조회 권한·FORCE RLS 해제·필수 함수 권한 누락·역할 멤버십 차단 및 기존 A/B API·Slack 모의 전송 회귀 통과. 실제 스테이징 세 역할도 읽기 전용 검사 통과. 기동 명령은 DB 접근·자식 시작 전에 종료 코드 1과 SAAS_RELEASE_NOT_READY로 차단됨을 확인했다. 운영 변경 없음.
