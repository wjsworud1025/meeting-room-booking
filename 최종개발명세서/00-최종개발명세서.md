# 회의실 예약 시스템 최종 개발명세서 v1.1

작성일: 2026-09-22 · 대상: 단일 교육기관, 학생 100~200명, 초기 회의실 5개

## 1. 문서 구성과 적용 기준

| 문서 | 답하는 질문 | 사용 대상 |
| --- | --- | --- |
| [기능 구현 명세](./01-기능구현명세.md) | 사용자가 무엇을 할 수 있고, 어떤 규칙으로 허용·거절하는가? | 기획·디자인·기능 개발·인수 검수 |
| [시스템 구현 명세](./02-시스템구현명세.md) | 그 동작을 어떤 구조와 데이터·API·배포 방식으로 보장하는가? | 개발·테스트·운영 |
| 본 문서 | 범위, 문서 간 연결, 개발 순서, 출시 조건은 무엇인가? | 전체 참여자 |

기능 요구사항은 F-번호, 시스템 요구사항은 S-번호, 인수 시나리오는 AT-번호로 식별한다. 두 구현 명세를 함께 적용한다. 기능 동작을 바꾸려면 기능 명세를, 동작을 유지하면서 구현만 바꾸려면 시스템 명세를 변경한다.

이 문서는 앞선 운영기획·구현계획·경량화 검토를 통합한 개발 기준이다. 기술 구성은 **상시 실행 앱 서버 1개 + Supabase PostgreSQL·Auth + 인증용 SMTP**로 정리한다. 별도 작업 서버는 두지 않는다. 슬랙은 조회·신청·초대·수락·거절·상태 확인·알림을 제공한다.

문서 완성은 구현·성능 검증·실제 서비스 설정 완료를 뜻하지 않는다. 본 명세에서 보완한 세부값은 개발 기본값이며 과거 대화에서 모두 개별 승인된 사항이라는 의미가 아니다. 도입 환경에 관한 정보는 아래 출시 전 준비사항으로 관리한다.

v1.1은 관리자 계정 생명주기(F-16·S-14)를 추가한다. 학생·관리자 전용 계정, 최초 관리자 등록, 관리자 초대·회수·복구와 관리자 보호 규칙을 포함한다. 업무 테이블 14개와 앱 서버 1개는 유지한다. 이전 목업의 관리자 메뉴에는 후속 UI 구현에서 '관리자 계정 관리'를 추가해야 한다.

## 2. 이번 명세에서 정리한 경계

| 항목 | 최종 개발 기준 |
| --- | --- |
| 경량화 | 기능 유지형 경량안을 적용. 하나의 앱 프로세스에서 웹·슬랙 입력·시간 경계·알림 작업 처리 |
| 마감 판정시각 | 서버가 처리 순서를 확보한 뒤 읽은 시각. 전송·접수 자체는 마감 전 처리나 예약 성공을 보장하지 않음 |
| 관리자 시작 후 변경 | 취소·사유 기록·구성원 정정 가능. 시작된 예약의 방·시작·종료 시각을 다시 쓰는 기능은 없음 |
| 모집중 1건의 주체 | 최초 신청자 기준. 책임 이전 시 새 책임자의 모집중·보충중 관리 건수도 검사 |
| 더 큰 범위 축소안 | 슬랙을 링크만 제공하는 방식, 15초 갱신, 공정성 축소, 일일 백업만 사용하는 안은 채택하지 않음 |

기능 명세의 시작 전·후 권한표, 판정 명단표, 예외 처리가 구현 기준이다. 이전 문서와 위 내용이 다른 경우 본 명세를 따른다. 신규 도입자의 첫 화면에는 기술 구현 설명 대신 이용 규칙과 행동 결과를 표시한다.

개발 중 임의 판단을 줄이기 위해 미정이던 세부 동작도 다음과 같이 채웠다. 보충중 자진 취소에는 10분 신청 제한을 적용하고, 확정 예약을 최소 인원이 부족한 큰 방으로 이동하는 변경은 거절한다. 슬랙 미연결 학생에게는 이메일로 필수 알림을 제공한다. 3운영일 제재 계산과 계정 비활성화 시 미완료 책임 이전의 처리도 기능 명세에 정의한다. 이는 이번 명세에서 정리한 기본 동작이다.

## 3. 제공 범위

| 구분 | 포함 |
| --- | --- |
| 학생 | 등록 계정 로그인, 시간표, 신청, 초대·응답, 참여 취소, 예약 변경·취소, 책임 이전, 내 예약, 신고 |
| 관리자 | 학생 일괄 등록·개별 추가·비활성화, 관리자 계정 초대·회수, 방·운영 설정, 휴관 영향 처리, 예약 개입, 신고·이용 제한, 변경 이력 |
| 슬랙 | 계정 연결, 조회·신청·초대·수락·거절·상태 확인, 개인 알림 |
| 시스템 | 충돌 방지, 기한 처리, 중복 요청 방지, 작업 재개, 개인정보 보호, 백업·복구, 핵심 검증 |
| 제외 | 출석 인증, 학생 조기 종료, 모임명, 개인별 하루 총량 제한, 반복 예약, 대기 순번, 자동 방 배정, 배치도, 공개 다기관 가입·결제, 다른 업무 도구 |

방 이름·정원·개수·시간 정책은 변경 가능하다. 다른 기관에는 별도 설치로 제공한다. 기관 여러 개를 하나의 DB에서 서비스하는 기능은 첫 버전에 포함하지 않는다.

## 5. 개발 순서와 산출물

숙련된 풀스택 개발자 1명, 집중 작업, 외부 계정 승인 대기 제외 기준의 작업량 추정이다. 기능·시스템을 문서상 분리하되 구현은 작은 사용자 흐름 단위로 연결한다.

| 단계 | 시스템 작업 | 기능 작업 | 완료 산출물 | 예상 |
| --- | --- | --- | --- | --- |
| 1 | 단일 서버·DB·인증·작업 재개·최초 관리자 등록 검증 | 로그인·학생 등록 | 실행 프로젝트, 초기 마이그레이션, 시험 계정 | 4~5작업일 |
| 2 | 트랜잭션·제약·시간 경계·재실행 처리 | 신청·수락·공정성·변경·취소·이전 | 실제 DB의 최소 예약 흐름과 경합 검사 | 6~8작업일 |
| 3 | 권한별 조회·화면 갱신·관리 API | 학생·관리자 전체 웹·관리자 계정 관리 | 웹에서 운영 가능한 통합판 | 6~8작업일 |
| 4 | 슬랙 연결·서명·tasks 전송 | 슬랙 흐름·알림 | 시험 워크스페이스 통합판 | 3~5작업일 |
| 5 | 부하·재시작·배포·복구·관리 권한 복구 검증 | 모바일·예외 안내·인수 검수 | 검증 결과, 배포 설정, 운영 안내 | 4~7작업일 |

합계 23~33작업일, 이후 시범 운영 2주다. 관리자 계정 관리·복구 검증 추가분 2~3작업일을 기존 추정에 반영했다. 경량화만으로 일정 단축을 보장하지 않는다. 웹만 완성된 단계에서는 웹 시범 운영이 가능하지만 슬랙까지 포함한 전체 완료로 처리하지 않는다.

## 6. 출시 전 준비사항

| 준비사항 | 필요한 결과 | 준비 전 진행 가능한 작업 |
| --- | --- | --- |
| 이메일 | 발신 도메인·SMTP·초대받을 학생 이메일 확인 | 가상 계정 기반 개발·메일 템플릿 검증 |
| 슬랙 | 기관 워크스페이스 앱 설치 권한·시험용 접근 | 요청 변환·서명·정책·실패 처리 개발 |
| 배포·비용 | 상시 앱·DB·백업의 운영 계정과 비용 한도 | 로컬 및 개발 환경 검증 |
| 운영·개인정보 | 최초 관리자 이메일, 기관 책임자·배포 운영자의 복구 연락 절차, 보존기간·개인정보 안내 | 기본값을 사용한 관리 기능 개발 |

계정·요금제·도메인 이름은 환경설정값이며 문서상 임의로 발급된 것으로 취급하지 않는다. 운영 권한과 비용 지출은 실제 배포 단계에서 확인한다.

## 7. 최종 인수와 완료 정의

기능 명세의 AT 시나리오와 시스템 명세의 검증표를 통과하고 결과를 기록해야 한다. 지표는 목표값이며 현재 달성값이 아니다.

| 인수 항목 | 조건 |
| --- | --- |
| 예약 무결성 | 방 중복 확정·개인 동시간대 중복 참여·정원 초과 0건 |
| 기능 완결성 | 학생·관리자 웹과 관리자 계정 생명주기 전체 흐름, 슬랙 목표 흐름, 권한·기한·공정성 예외 구현 |
| 성능 | 동시 사용 100명 조건에서 조회·신청·수락 응답 p95 2초 이내, 정상 연결 화면 반영 5초 이내 |
| 외부 작업 | 정상 외부 연동에서 알림 전송 처리의 95%가 30초 이내, 재시작 후 유실 없이 재개 |
| 복구 | 최대 1시간 데이터 손실 목표와 운영 중 2시간 이내 복구 목표를 실제 시험하고 운영 담당자가 절차 확인 |

배포 결과물에는 소스·lockfile·SQL 마이그레이션·가상 seed·환경변수 목록·검증 실행법·백업 복구 절차·관리자 안내를 포함한다. 운영 비밀키와 실제 학생 명단은 저장소에 넣지 않는다.
