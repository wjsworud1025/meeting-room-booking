# SaaS Slack 클래스·알림 작업 격리

2026-09-30 / codex/saas-data-isolation

## 구현

1. 클래스 설치: 고객의 일회용 설치 링크를 서비스 제어 영역에서 조회한다. OAuth의 서명된 state·브라우저 cookie·Slack 응답 검증을 유지하고, callback에서 링크의 고객에게만 workspace route/설치 토큰/클래스를 원자적으로 저장한다. 다른 고객 또는 다른 클래스에 연결된 team_id는 덮어쓰지 않는다. 만료·사용된 링크는 거부한다.
2. Slack 요청: Socket Mode SDK의 인증된 context.teamId로 고객을 결정한다. authorize와 이벤트/액션 처리 모두 해당 고객의 RLS 트랜잭션 안에서 실행한다. SaaS에서는 환경변수의 공용 봇 토큰으로 fallback하지 않는다. 워크스페이스를 바꾸는 중첩 호출도 거부한다.
3. 웹 진입: 단기 진입 토큰의 hash로 고객만 확인한 뒤 해당 고객 안에서 일회용 토큰을 소비한다. 서버가 봉인한 Slack 세션의 team을 기준으로 일반 API 고객을 결정하고 기존 Slack 사용자 검증도 수행한다. ID 로그인 cookie와 Slack cookie 충돌은 진입 시 정리한다. 기존 이메일/Slack OIDC 로그인은 SaaS 모드에서 아직 차단하며 ID 로그인과 앱 홈 진입을 사용한다.
4. 자동 알림: 별도 스케줄러 역할이 작업 ID·tenant_id·lease_token만 선점한다. payload/수신자/예약/봇 토큰은 비특권 업무 역할로 해당 고객 안에서만 읽는다. 발송 직전에 고객·수신자 상태와 lease, 워크스페이스 연결 상태를 다시 확인한다. 완료·재시도 갱신은 작업 ID와 lease가 모두 일치할 때만 수행한다.
5. 유지관리: 고객별 예약 만료/종료 처리와 명단 동기화를 실행한다. 명단 동기화의 실행/주기 상태도 고객별로 분리했다. 같은 Slack user_id가 다른 워크스페이스에 있어도 고객별 구성원으로 유지한다.

## DB 역할과 적용

별도 검증 DB에 001_candidate → 002_web_runtime → 003_slack_workers 순으로 적용한다. 자동 운영 migration 경로에는 넣지 않았다.

| 연결 | 권한 |
|---|---|
| DATABASE_URL | 기존 비특권 업무 역할. 고객 테이블 CRUD/RLS, 공휴일 원본 SELECT |
| CONTROL_DATABASE_URL | identity 인증 + account_route/create_space + install_preview/connect_install/workspace_route/web_link_route 실행. booking 직접 조회 금지 |
| WORKER_DATABASE_URL | claim_notification/delivery_allowed/maintenance_tenants 실행만 허용. booking payload 직접 조회 금지 |

권한 부여와 역할 분리의 실행 예시는 tests/saas-web-integration.ts에 포함되어 있다. 함수의 PUBLIC 실행권한은 모두 제거되어 있다. 운영자는 마이그레이션 계정을 앱 환경에 주입하지 않는다.

## 검증 결과

`npm run test:saas:web`의 합성 데이터 테스트에서 다음을 확인했다.

| 항목 | 결과 |
|---|---|
| 고객 A/B 설치·명단 | 각자의 workspace/class에 연결, 동일 Slack user_id도 별도 등록 |
| 설치 링크 재사용·만료 | 차단 |
| B가 A의 workspace로 설치 | DB 유일성 제약으로 차단, 기존 A 토큰 유지 |
| 다른 고객 컨텍스트로 워크스페이스 사용 | 거부 |
| 알림 2건 동시 선점 | A/B 각각 자신의 봇 토큰·수신자·예약 내용 사용 |
| 잘못된 예약 ID를 넣은 작업 | 외부 호출 없이 재시도 상태로 기록 |
| 작업 선점 직후 고객 정지 | 발송 직전 재검사로 차단 |
| 스케줄러가 작업 payload 직접 SELECT | DB 권한으로 거부 |

DM 전송은 실제 runTask 경로에서 fetch를 모의 응답으로 대체해 검증했다. 실제 Slack 워크스페이스/사용자에게 메시지를 보내지 않았다. Socket Mode 수신, Slack API를 통한 사용자 검증 및 실제 앱 홈 표시/DM 도착은 운영 전 별도 시험이 필요하다.

## 운영 한계와 다음 단계

- 아직 Railway 배포·운영 데이터 이관은 수행하지 않았다. start-railway의 SaaS 출시 차단은 유지한다.
- 현재 SaaS 선점 대상은 NOTIFY다. HOLIDAY_SYNC는 공통 원본 캐시 전용 작업자로, MEMBER_PROVISION은 SaaS 가입 정책에 맞춰 별도 전환해야 한다. 기존 비-SaaS 작업은 계속 기존 경로를 사용한다.
- 외부 메시지 성공 직후 DB 완료 기록 전에 프로세스가 종료되면 재시도로 중복될 수 있다. 정확히 한 번 전송을 보장하지 않는다. lease는 120초이며 실패는 5분 후 재시도, 4회 후 FAILED로 남긴다.
- 고객 정지/삭제와 외부 Slack 전송 사이에는 분산 트랜잭션이 없다. 발송 직전 상태 재검사는 완료했지만 이미 Slack이 접수한 메시지를 취소하지는 않는다.
- 다음은 비공개 스테이징의 A/B 워크스페이스에서 실제 설치 → 구성원 등록 → 예약 → DM/앱 홈 도착을 확인하고, 공휴일 공통 작업자 및 배포 역할 구성을 마무리하는 것이다.

최종 회귀 검사: 계정 통합 검사, 21개 테이블 DB 격리 검사, 단위 테스트 19개 파일/121개 테스트 및 프로덕션 빌드 통과. 기존 단위 테스트의 DB mock에는 비-SaaS 모드를 명시하여 이전 동작을 검증했다.


## 2026-09-30 최종 후속 검증

이 절은 앞선 중간 점검의 미완료 목록을 갱신한다. 공휴일 공유 작업(004), 내보내기·ID 기반 소유권 이전·삭제 대기/취소(005), 비특권 역할 설치·검사와 별도 워커를 구현했다. 실제 API·DB의 고객 A/B 격리와 수명주기 통합 검사를 통과했다. 영구 삭제는 합성 DB에서만 검증했고 운영 실행은 차단한다.

승인된 최신 암호화 백업 railway-1790744899443은 24개 테이블(업무 274행, 마이그레이션 15행, import 1행)과 공휴일 시퀀스를 포함한다. 네트워크 없는 PostgreSQL 18.6 컨테이너에서 016 및 후보 001–005 적용·롤백 후 24개 테이블 지문이 일치했다. 설치 토큰의 현재 키 복호화도 확인했다. 임시 컨테이너와 SSH 키 등록은 정리했다. 운영 원본은 변경하지 않았다.

운영 전환에는 별도 삭제 원장 보존·백업 30일 만료 검증, 운영용 제한 역할 적용, 두 실제 Slack 구성원 검증이 남아 있다. 현재 두 번째 Slack 계정이 없어 모의 검증으로 대체 완료하지 않는다. 상세 기준은 [수명주기 검증](SaaS-수명주기-검증.md)과 [운영 전환 절차](SaaS-운영전환-복구절차.md)를 따른다.
