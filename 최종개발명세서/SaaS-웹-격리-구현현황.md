# SaaS 웹 API 고객 격리 구현 현황

2026-09-30 / codex/saas-data-isolation

## 완료한 단계

| 영역 | 구현 |
|---|---|
| 신규 고객 시작 | ID 가입·로그인 → 내 운영 공간 이름 입력 → 소유 계정당 1개 공간 생성. 중복 요청은 기존 공간을 반환한다. |
| 초기 데이터 | 신규 공간에 ADMIN, 기본 수업장, 빈 회의실 정책, 고객별 설정/공휴일 검토 행을 생성한다. 다른 고객 데이터는 복사하지 않는다. |
| 요청 경계 | 서버 세션의 account_id로 제어 영역에서 tenant/member를 결정한다. URL/본문/헤더의 tenant_id는 사용하지 않는다. |
| DB 접근 | 인증 제어 역할과 예약 업무 역할을 분리한다. 제어 역할은 예약 테이블을 직접 읽을 수 없고, 웹 역할은 identity 테이블을 읽을 수 없다. 특권 역할은 요청 경계에서 거부한다. |
| 예약/관리자 API | AsyncLocalStorage에 요청 전용 트랜잭션 연결을 보관한다. 기존 조회·command가 같은 SET LOCAL 고객 컨텍스트와 RLS를 사용한다. 중첩 transaction은 savepoint로 처리하고 바깥 요청이 최종 commit/rollback을 결정한다. 종료 후 연결 핸들 사용은 거부한다. |

SaaS 모드에서 컨텍스트 밖의 pool() 접근은 즉시 실패한다. 회원 식별자·회의실 UUID를 알고 있어도 다른 고객의 행은 조회되지 않는다. 설정 행 잠금, UPSERT의 이메일/작업키/휴일 충돌 키도 고객 범위로 변경했다. 정책 JSON에 현재 고객에게 없는 회의실 키를 넣는 요청도 거부한다.

## 동작 조건

- 기존 로컬/운영 환경은 SAAS_ENABLED를 설정하지 않아 기존 동작을 유지한다.
- 별도 검증 DB에서 기존 001~016, 준비 SQL 001_candidate, 002_web_runtime 순으로 적용한다. 준비 SQL은 자동 마이그레이션 경로에 넣지 않는다.
- DATABASE_URL은 비특권 웹 역할, CONTROL_DATABASE_URL은 비특권 인증 제어 역할이다. 데이터 이관 계정은 앱에 제공하지 않는다.
- 역할 권한의 실행 가능한 예시는 tests/saas-web-integration.ts에 있다. 웹은 고객 테이블 CRUD와 공휴일 캐시 SELECT/current_tenant 실행만, 제어 역할은 identity 계정/세션과 account_route/create_space 실행만 갖는다.
- SAAS_ENABLED=true인 검증 환경에서 /account에 운영 공간 생성 폼이 나타난다. 운영 Railway의 SaaS 활성화는 start-railway.mjs가 명시적으로 차단한다.

## 검증

`npm run test:saas:web`은 외부 서비스 없이 임시 DB와 실제 Next.js GET/POST 핸들러를 사용한다.

1. 기존 hyundai_1st 로그인 및 새 고객 가입/로그인/공간 생성/재시도.
2. A/B 관리자 데이터·회의실 생성·시간표 조회와 교차 수정 차단.
3. 실제 예약 업무 명령으로 A 예약 생성, B의 해당 예약 상세 404, 다른 고객 회의실·구성원 지정 거부.
4. 생성된 알림 작업이 A에게만 존재함, 무컨텍스트 조회 0행, identity 직접 조회 거부, 종료된 연결 사용 거부.
5. 로그아웃 세션 재사용 거부, SaaS 모드의 미전환 Slack 인증 차단.

기존 계정/이관 통합 검사와 단위 테스트 121개, TypeScript 및 프로덕션 빌드도 확인한다. 실제 Slack 수신/DM 또는 작업 실행 검증을 완료했다고 해석하지 않는다.

## 아직 열지 않은 경로

Slack OAuth/Socket Mode/설치 콜백·웹 진입 토큰 라우팅 및 자동 작업자의 선점·실행 경계가 아직 전환되지 않았다. SaaS 모드에서는 기존 Slack 프로세스·자동 작업을 실행하지 않고 설치 요청 생성도 차단한다. 기존 비-SaaS 운영 서비스의 Slack/작업은 그대로 유지한다.

신규 고객이 학생을 연결해 운영하는 전체 서비스는 아직 출시 준비가 끝나지 않았다. 다음 단계는 **서명 검증된 Slack team_id / 설치 토큰 → 고객 라우팅**과 **제한된 작업 선점 → 고객별 실행**을 구현하고, 외부 알림 전송까지 검증하는 것이다. 현재 로컬 DB나 Railway의 스키마/계정 상태를 SaaS로 전환하지 않았다.


후속 업데이트: Slack 클래스·NOTIFY 작업의 고객 경계를 구현하고 모의 전송 검증을 완료했다. 위 미완료 경로 설명은 웹 API 단계 당시의 기록이다. 최신 범위와 남은 제약은 [Slack·알림 격리](SaaS-Slack-알림-격리.md)를 참고한다.
