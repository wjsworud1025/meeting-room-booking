# SaaS 데이터 격리·이관 준비 (v1.0)

2026-09-30 · 브랜치 `codex/saas-data-isolation` · 기준 커밋 `a63887c`

현재 운영 전환 조건은 [SaaS 운영전환·복구절차](../../최종개발명세서/SaaS-운영전환-복구절차.md)를 기준으로 한다. 아래 초기 검증·미완료 표에는 이후 해결된 항목이 포함되어 있으며, 실제 운영 승인 데이터 복원과 API·Slack 검증 결과는 연결된 최신 보고서를 참고한다.

**검증용 후보이며 운영에 적용하지 않는다.** 기존 서버는 고객 컨텍스트 없이 SQL을 실행하므로 이 SQL만 적용하면 서비스가 중단된다. 자동 적용 경로 `db/migrations`와 의도적으로 분리했다. 이번 작업은 명세의 데이터 이관·격리 기반 준비이며 SaaS 전환 완료가 아니다.

## 준비한 내용

1. 기존 활성 ADMIN을 이메일 하드코딩 없이 첫 고객 OWNER/account에 연결한다. 원래 member UUID, 예약, 감사 기록, 암호화된 Slack 토큰은 보존한다. auth_subject가 없는 기존 계정은 NULL로 두며 이메일 인증 완료를 만들어내지 않는다.
2. 고객 소유 21개 테이블에 tenant_id를 채우고 NOT NULL·복합 FK·고객별 UNIQUE·예약 충돌 제약을 구성한다. 공휴일 원본 holiday_years만 공통 캐시로 유지한다. 고객별 공휴일 검토/수정은 격리한다.
3. 계정·고객·워크스페이스 라우팅은 saas_control로 분리한다. team_id는 서비스 전체에서 유일하다. OWNER/account/member 일치를 지연 제약 트리거로 확인한다.
4. 모든 고객 테이블에 FORCE RLS와 USING/WITH CHECK를 적용한다. 컨텍스트가 없으면 읽기는 0행, 쓰기는 거부한다. 정지된 고객도 거부한다. tenantTransaction은 트랜잭션 로컬 컨텍스트·고객별 settings 잠금·오류 롤백을 제공한다.
5. 스키마 목록을 대조하고 알 수 없는 테이블·누락된 테이블·소유자 불일치 시 중단한다. 원래 모든 열의 행수와 지문을 비교하며 개인정보나 토큰 내용을 출력하지 않는다. 중복 적용도 중단한다.

## 실행

프로젝트 루트에서 실행한다. `.env.local`의 DATABASE_URL을 사용하며 인증정보를 출력하지 않는다.

```powershell
npm run saas:preflight
npm run saas:dry-run
npm run test:saas
```

- preflight: 읽기 전용. 현재 스키마·단일 활성 ADMIN·settings·행수를 확인한다.
- dry-run: APP_ENV=local, 루프백 DB만 허용한다. 전체 이관 및 데이터 보존 검증 후 **항상 ROLLBACK**한다. 적용 명령은 없다. 테이블 잠금이 있으므로 서비스가 사용하지 않는 복원 DB에서 실행한다. 잠금 대기 3초, 각 SQL 제한 60초.
- test:saas: 기존 001~016 마이그레이션으로 임시 DB를 만든다. 합성 데이터와 비특권 LOGIN 역할로 검증한 후 **이 테스트가 생성한 DB/역할만** 삭제한다. 원래 DB는 건드리지 않는다. 로컬 테스트 계정에 CREATE DATABASE/ROLE 권한이 필요하다.

후보 실행 계정은 격리된 복원 환경의 마이그레이션 계정(SUPERUSER 또는 BYPASSRLS)이다. 이 권한을 웹/일반 작업 프로세스에 제공하면 안 된다. 현재 후보의 소유자 검증 함수는 이 마이그레이션 계정 소유의 고정 search_path SECURITY DEFINER이며 PUBLIC 실행권한은 제거된다. 런타임에는 saas_control 테이블 권한을 주지 않고 current_tenant 실행권한만 부여한다. 실제 역할 설치 SQL은 운영 전환 시 별도 작성해야 한다.

## 검증 결과

- TypeScript 검사 통과, 기존 단위 테스트 19개 파일 / 121개 테스트 통과.
- SaaS 전용 PostgreSQL 통합 검사 통과: 첫 고객 이관 전후 원본 지문 일치, 롤백, 중복 적용 거부, 모든 고객 테이블의 무컨텍스트 차단.
- 고객 A/B 조회·수정·INSERT·tenant_id 변경·교차 FK 차단, OWNER 일치, 같은 이름/정책 날짜/작업 키/휴일 사용, Slack 소유권 탈취 차단.
- 단일 연결 풀의 성공/오류 뒤 컨텍스트 제거, 고객 정지, 고객별 독립 잠금, 특권 런타임 역할 거부 확인.
- 현재 로컬 DB는 015의 class_install_requests가 없어 일반 드라이런이 사전검사에서 중단됨. 별도 로컬 리허설에서 015와 후보를 같은 트랜잭션에 임시 적용해 기존 164행 보존을 확인하고 모두 롤백함. 015 테이블과 saas_control이 남지 않은 것도 확인함. 운영 백업 복원 검증은 아직 수행하지 않음.

## 운영 전환을 막는 미완료 항목

| 경계 | 현재 상태 / 다음 작업 |
|---|---|
| 인증·세션·예약·관리자 API | 기존 전역 pool()/transaction()을 사용한다. 서버에서 검증한 tenant를 해석하고 tenantTransaction 안에서 모든 SQL을 실행해야 한다. 헬퍼 인자만으로 인증되는 것은 아니다. 클라이언트 tenant_id를 그대로 전달하면 안 된다. |
| DB 역할·배포 | start-railway.mjs가 앱 DATABASE_URL로 자동 마이그레이션한다. 배포 전용 마이그레이션 역할과 비특권 웹/작업 역할을 분리하고 앱에서 이관 자격증명을 제거해야 한다. |
| Slack·작업·캐시 | 서명 검증 후 최소 라우팅 조회, 고객별 작업 선점/처리/재시도, 알림 전 고객 상태 재검사, 캐시 키의 tenant 범위가 필요하다. 기존 전역 작업 루프를 그대로 실행하면 안 된다. |
| JSON·스냅샷 | policy rules.rooms, 예약 참여자 UUID 배열, task payload, 감사 entity_id는 기존 FK가 없는 참조다. 구조화 FK 외의 고객 소속 검증은 업무 경로 전환 때 추가해야 한다. RLS가 JSON 내부 UUID까지 검사하지는 않는다. |
| 출시·이관 | 운영 백업 복원, 데이터/암호화키 대조, 신규 고객 시작·소유권 이전·내보내기·탈퇴, A/B 실제 API·Slack 통합 검증이 남아 있다. 현재 신규 고객을 활성화하면 안 된다. |

## 실제 이관 순서

1. 운영 백업을 별도 비공개 DB에 복원하고 최신 001~016 적용 상태를 확인한다. 복원 DB에서는 Slack·메일·자동 작업을 실행하지 않는다.
2. 사전검사와 드라이런을 실행한다. 실패한 스키마/참조/소유자 원인을 해결하고 원본 데이터 보존 보고서를 확보한다. 후보를 자동 migration 폴더로 옮기지 않는다.
3. 런타임의 인증·API·작업·캐시를 tenant 경계로 전환하고 실제 비특권 역할로 A/B 통합 테스트를 완료한다. 무중단이 필요하면 별도 expand/dual-write/backfill/cutover 단계로 분할한다. 현재 후보는 최종 형태를 한 트랜잭션에서 리허설하는 도구다.
4. 쓰기 중지·워커 정지 후 백업, 전용 이관 작업, 스키마와 앱 버전 동시 전환, 기능 확인을 진행한다. 첫 고객 정상 동작 확인 전 두 번째 고객 가입을 열지 않는다.
5. 전환 실패 시 서비스를 멈추고 사전 백업과 이전 앱 버전을 함께 복원한다. 전환 후 신규 쓰기가 생기면 단순 다운마이그레이션하지 않고 복원/재처리 계획을 별도로 확정한다.


## 로그인 ID 도입 후 업데이트

`016_login_accounts.sql`은 기존 데이터 테이블과 분리된 identity 스키마만 추가한다. `identity.legacy_owner`가 현재 단일 고객 데이터의 소유 계정과 기존 ADMIN member를 연결한다. SaaS 후보는 이 연결이 있으면 같은 account UUID를 첫 tenant의 OWNER로 사용한다. 아직 모든 운영 행에 tenant_id를 적용한 상태는 아니다.

로컬에 015·016을 정상 적용하고 `hyundai_1st`를 연결했다. 과거 드라이런의 015 누락은 해결되었다. 신규 가입 계정은 PENDING이며 레거시 예약 API 접근이 거부된다. SaaS 런타임 전환 전에는 ACTIVE로 수동 변경하지 않는다. 자세한 인증 동작은 `최종개발명세서/로그인-ID-구현현황.md`를 참고한다.
